# ADR 0001: Order aggregate, Catalog quotes and durable idempotency

> Историческое решение. Актуальный жизненный цикл заказа, POS-оплата и события
> исполнения определены в [ADR 0003](0003-pos-fulfillment.md).


Дата: 2026-10-17. Статус: принято.

## Контекст

Нужно создавать заказы по актуальному меню, сохранять подтверждённую клиентом
стоимость блюд и безопасно повторять запросы после потери ответа. Catalog уже
владеет ресторанами и меню. Оплата, доставка и резервирование не реализуются.

## Границы данных и зависимостей

Orders — отдельный Go-модуль с собственной PostgreSQL database `orders` и ролью
`orders_service`. Catalog использует свою database и `catalog_service`. Compose
отзывает PUBLIC CONNECT и не передаёт сервисам superuser credentials. Общий
PostgreSQL instance уменьшает стоимость локального окружения, но остаётся общей
точкой отказа; базы можно перенести на разные instances без изменения domain.
FK на Catalog отсутствуют: удаление или изменение меню не должно менять историю
заказа. `init-databases` также переносит ownership таблиц старого Compose Catalog
с bootstrap superuser на `catalog_service`, сохраняя volume и данные.

Направление runtime-вызова: **Orders → Catalog**, ответ идёт Catalog → Orders.
Импортов между Go-модулями нет. HTTP-контракт — независимая граница. Domain не
зависит от JSON/HTTP/pgx. Application определяет OrderRepository и CatalogClient;
адаптеры реализуют порты. Bootstrap соединяет их конструкторами. Благодаря этому
инварианты тестируются без БД, use cases — через небольшие стабы портов, транспорт
— через httptest, SQL-конкурентность — отдельно на настоящей PostgreSQL.

## Order как Aggregate Root

Order управляет всеми OrderItem: нельзя добавить отдельную позицию, изменить её
цену или напрямую установить статус. Поля агрегата закрыты, Snapshot возвращает
копию, Restore проверяет сохранённые суммы. Публичные структуры состояния нужны
для persistence, но их изменение не меняет существующий Order. Снимки имени и
цены неизменяемы. Единственная мутация агрегата — Cancel из PENDING_PAYMENT в
CANCELLED; повторная отмена возвращает конфликт. Других статусов пока нет.

Цена в int64 minimal units, валюта только TJS. До умножения проверяется
`price <= MaxInt64 / quantity`, до сложения — `subtotal <= MaxInt64 - total`.
Лимиты — 100 уникальных позиций, 1–100 единиц каждой. Повтор MenuItemID запрещён,
порядок позиций не влияет на смысл запроса. Money VO не введён: нет конвертации,
округления или арифметики разных валют; инварианты сосредоточены в конструкторе
агрегата. Отдельный слой Money сейчас только дублировал бы эти проверки.

## Quote и подтверждение стоимости

Orders отправляет один POST /internal/v1/menu/quote с restaurant_id и парами
menu_item_id/quantity. Catalog одним SQL statement получает restaurant.is_open
и все запрошенные блюда в одном MVCC snapshot, включая проверку soft delete.
Application Catalog проверяет наличие, принадлежность и доступность. Возвращаются
имена, цены, количества, restaurant_id и TJS; Order adapter проверяет полноту и
соответствие ответа запросу. HTTP-ошибки quote имеют стандартное поле `error`
и машинный `code`; неизвестные коды/5xx/некорректные ответы/таймауты считаются
временной недоступностью (Orders 503), бизнес-ошибки — 404/409. Redirect запрещён,
response body ограничен 256 KiB и закрывается. Клиент и request context задают
два ограничителя времени; Catalog timeout меньше общего request deadline.

Клиент не задаёт цену позиции. Иначе он мог бы купить любое блюдо за 1 minimal
unit. expected_subtotal_minor — подтверждение, а не источник цены: Order считает
subtotal по Catalog и при несовпадении возвращает 409, ничего не сохраняет.
Клиент обновляет меню и подтверждает новую сумму отдельным запросом/новым ключом.
Subtotal — стоимость только блюд, без доставки, налогов и скидок.

Quote **не резервирует** блюда и не блокирует Catalog после ответа. Меню или
доступность могут измениться сразу после снимка, даже до сохранения заказа.
Заказ фиксирует полученный снимок, но не гарантирует дальнейшую возможность
исполнения. Межсервисной транзакции нет; её имитация блокировкой БД Orders не
решила бы задачу. Резервирование требует отдельного бизнес-процесса.

## Идемпотентность и SQL-транзакции

Обязателен printable ASCII Idempotency-Key длиной 1–128, без пробелов. Область
уникальности — (CustomerID, key), а не глобальный key. SHA-256 считается по
нормализованной команде: customer, restaurant, currency, expected subtotal и
отсортированные позиции/количества. JSON whitespace и порядок позиций не влияют
на hash; изменение количества, ресторана, суммы или валюты меняет содержание.

1. До Catalog читается idempotency_keys: тот же hash возвращает исходный ответ,
   другой hash даёт 409. HTTP не вызывается при успешном повторе.
2. Catalog вызывается без открытой SQL-транзакции.
3. Короткая транзакция вставляет orders и order_items, затем idempotency_keys
   вместе с исходным результатом создания в JSONB. PRIMARY KEY(customer_id,key)
   определяет победителя. INSERT ON CONFLICT DO NOTHING ожидает результат
   конкурирующей транзакции. Проигравший откатывает ВСЕ свои строки, затем читает
   победивший результат и сравнивает hash. Пропуски identity ID допустимы.
4. Commit делает заказ, позиции и результат повтора видимыми вместе. Если клиент
   потерял ответ после commit, повтор вернёт сохранённый результат. При ошибке
   последней записи весь заказ откатывается. При неопределённом результате commit
   клиент повторяет тот же запрос с тем же ключом.

Сохраняются только успешные результаты, ошибки не закрепляют ключ. После ошибки
quote приложение повторно проверяет ключ: параллельный запрос мог уже успешно
создать заказ. Если победитель ещё не закоммитился, текущий запрос может вернуть
бизнес-ошибку; последующий повтор найдёт исходный результат. Дубликат не создаётся.
Одинаковые успешные запросы всегда возвращают 201 с исходным body/Location, в том
числе после изменения цен, отмены, удаления блюда и перезапуска сервиса.
GET /orders/{id} показывает текущее состояние, replay POST — исходное создание.
JSONB хранит persistence snapshot, HTTP DTO формируется отдельно. При изменении
формата State в будущем необходима совместимость с сохранёнными результатами.

Ключи пока не удаляются и не имеют TTL: очистка изменила бы гарантию повторов и
потребует отдельного решения о сроке хранения. Это сознательный расход места.

Cancel выполняет SELECT ... FOR UPDATE OF orders, загружает агрегат, вызывает
доменный Cancel и обновляет статус/updated_at в одной транзакции. Конкурентная
отмена увидит уже CANCELLED. Все чтения/мутации фильтруются по CustomerID; чужой
ID даёт 404. Get читает заказ и позиции одним JOIN, одним snapshot. Снимки позиций
вообще не обновляются. FK/CHECK/UNIQUE дополняют проверки domain, однако сумма по
всем строкам и непустота агрегата обеспечиваются конструктором и атомарной записью.

Отдельный TransactionManager/UnitOfWork не нужен: каждая атомарная операция
затрагивает только один OrderRepository. Callback Cancel позволяет application
вызывать domain под блокировкой, сохраняя pgx внутри адаптера.

## Сеть и идентификация

Публичный Catalog listener не регистрирует /internal. В Compose quote listener
привязан к адресу backend alias catalog-internal, порт 8082 не опубликован;
backend имеет internal:true. Публичные порты 8080/8081 публикуются только на
host loopback через edge network. Вне Compose внутренний адрес по умолчанию
127.0.0.1:8082. Этот Compose рассчитан на одну реплику Catalog; масштабирование
потребует явного binding/discovery внутреннего интерфейса для каждой реплики.

Для production необходимы service-to-service authentication (например, mTLS),
TLS, сетевые политики и настоящий identity adapter. Сеть сама не аутентифицирует
сервис: любой участник backend сейчас может вызвать quote. Не публиковать 8082
и не проксировать /internal наружу. Административный API Catalog всё ещё требует
отдельной авторизации перед публичным deployment.

Orders по умолчанию APP_ENV=production, DEV_AUTH_ENABLED=false: order endpoints
возвращают 401 до реализации настоящего identity adapter. Dev/test механизм
X-Dev-Customer-ID включается явно, имеет проверку положительного ID, не принимает
CustomerID в JSON и запрещён при production/неизвестном APP_ENV. Это возможность
для локальных тестов, а не защита от подмены пользователя. Compose включает её
для локальной разработки и ограничивает host ports loopback.

Readiness проверяет свою БД и схему; отказ Catalog не делает Orders unready,
чтобы оставались доступны Get, Cancel и успешные replay. Create без сохранённого
результата при отказе Catalog возвращает 503. Liveness не использует БД.
SIGTERM закрывает оба Catalog listener и Orders, ждёт запросы, затем закрывает
pool/idle HTTP connections; при превышении shutdown deadline соединения закрываются.

## Последовательность создания

```mermaid
sequenceDiagram
    actor Client
    participant HTTP as Orders HTTP
    participant App as Orders application
    participant ODB as Orders PostgreSQL
    participant Cat as Catalog internal HTTP
    participant CDB as Catalog PostgreSQL
    Client->>HTTP: POST /orders + identity + Idempotency-Key
    HTTP->>App: CreateOrder(command, key)
    App->>ODB: FindCreation(customer, key, hash)
    alt Успешный запрос уже сохранён
        ODB-->>App: Исходный результат (или конфликт hash)
        App-->>Client: 201 исходный Order / 409
    else Новый запрос
        App->>Cat: POST /internal/v1/menu/quote (все позиции)
        Cat->>CDB: Один SELECT: ресторан + блюда
        CDB-->>Cat: Согласованный снимок
        Cat-->>App: Имена, цены, валюта, количества
        App->>App: Domain.NewOrder + overflow checks + expected subtotal
        alt Сумма отличается
            App-->>Client: 409, заказ не сохранён
        else Сумма подтверждена
            App->>ODB: BEGIN, INSERT order + items + idempotency result
            Note over ODB: UNIQUE(customer_id, key); проигравший откатывается
            ODB-->>App: COMMIT / исходный результат победителя
            App-->>HTTP: Order
            HTTP-->>Client: 201 + Location + снимки позиций
        end
    end
```

## Проверка и последствия

Доменные тесты покрывают переполнения при умножении и сумме, снимки и state
machine. Use case/HTTP тесты проверяют валидацию, ошибки quote, подтверждение
цены, идентификацию и replay. Реальный httptest server проверяет Catalog adapter,
включая timeout/context. PostgreSQL tests проверяют атомарность, CHECK/FK, гонки
одинаковых и разных payload, изоляцию пользователей, отмену и сохранённый replay.
Отдельный E2E проверяет два собранных сервиса с их собственными базами.

Общих domain-библиотек, generic repositories, Redis, broker, outbox и новых
бизнес-сервисов не вводим. Без аутентификации production order API намеренно
закрыт; без резервирования заказ не является обещанием наличия.
