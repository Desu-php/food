# ADR 0013: Independent Auth Service

Статус: принято, Stage 18. Уточняет ADR 0006 и заменяет зависимость от login flow
в ADR 0012 после контролируемого переключения. Старый режим сохранён для миграции.

## Контекст

Quasar PWA должен использовать собственные формы Login/Register без редиректов.
Пароли, аккаунты, сессии и отзыв полномочий образуют отдельную границу данных.
Размещение этой ответственности в Orders сделало бы его владельцем чужого домена.
Существующий deployment-owned JSON registry требует согласованного рестарта API
и не подходит для регистрации и оперативного отзыва доступа.

## Решение

Независимый Go Auth Service владеет отдельной PostgreSQL. Domain содержит User,
статусы и инварианты, application — сценарии и порты, adapters — SQL, net/http,
Argon2id и JWT; bootstrap собирает зависимости конструкторами. Auth не владеет
заказами, ресторанами и доставками и не пишет таблицы остальных сервисов.

Публичная регистрация создаёт только customer. Глобальные роли, permissions,
restaurant memberships и customer/courier bindings хранятся в Auth. Deployment
administrator создаёт управляемые аккаунты через offline authctl с аудитом и
секретным stdin; действующий admin может менять grants через защищённый HTTP API.
Роль из frontend не является полномочием. CustomerID/CourierID сохраняются и после
отзыва роли, поэтому последующее назначение не меняет бизнес-идентичность.

Пароли хранятся как Argon2id PHC hashes со случайной 128-bit солью, ограниченными
проверяемыми work factors и ограничением параллельного потребления памяти.
Минимум — 15 символов, максимум — 1024 UTF-8 байта; длинные фразы допустимы.
PostgreSQL rate limits общие для реплик и переживают рестарт. Дубликаты регистрации
возвращают тот же 202; неизвестный email и неверный пароль — одинаковый 401 с
вычислением dummy hash. Незавершённый почтовый канал не заменяется фиктивной
проверкой email: публичные production-аккаунты остаются PENDING_VERIFICATION.

Access JWT живёт до трёх минут (конфигурируемо, максимум пять), подписывается ES256
и имеет protected typ=at+jwt. JWT содержит только opaque subject, session ID,
auth version и стандартные security claims. PWA держит его в памяти. Refresh —
256-bit opaque secret в HttpOnly Secure SameSite=Strict host-only cookie. БД
содержит только SHA-256 hash. User/session/token блокируются в едином порядке;
ротация и регистрация consumed token фиксируются атомарно. Повторное использование
отзывает всю сессию. Конкурентные refresh также считаются reuse; frontend должен
сериализовать их между вкладками. Сетевой сбой после commit требует нового login,
поскольку сервер не хранит plaintext successor для повторной выдачи.

Cookie mutations требуют точного Origin, JSON и привязанного к refresh cookie
CSRF-токена. Последний можно восстановить отдельным защищённым GET csrf после
reload. CORS разрешает credentials только Auth endpoints для точных origins.
Остальные API используют Bearer и не меняют модель CORS на cookie authentication.

platform/security сначала проверяет JWT по доверенным issuer/JWKS, API audience,
signature, exp, nbf и allowlist алгоритмов, затем вызывает закрытый Auth authority.
Auth повторно проверяет токен, текущую сессию, статус и auth_version и возвращает
актуальный Principal. Grants не берутся из JWT. Online resolution без кеширования
даёт немедленный отзыв на следующем запросе, включая административные операции.
Orders/Delivery получают эти полномочия через явную application authorization
dependency. Все существующие resource-level и domain gates остаются обязательными.

Notifications перед Send проверяет текущие права владельца устройства через Auth.
Изменение grants транзакционно создаёт задание отзыва устройств. Отдельный цикл
Auth использует PostgreSQL lease/fencing, закрывает SQL до HTTP и повторяет
идемпотентную команду Notifications. Только Notifications очищает свои identifiers.
Отправленные FCM сообщения отозвать невозможно; in-flight Send остаётся прежней
границей Stage 14.

## Миграция и последствия

Импорт старого registry атомарно сохраняет исходные UserID, CustomerID, CourierID,
RestaurantID и opaque Subject с legacy issuer в отдельной таблице. Конфликты
не разрешаются переназначением ID. Пароли и email не выдумываются: импортированные
аккаунты выключены до контролируемого назначения email/нового пароля. Новые ID
выдаются из зарезервированного диапазона от 10^12; перед rollout проверяются
фактические максимумы и полный список старых привязок.

После испытаний переключаются все API и worker на новый issuer/JWKS и authority;
ручной registry отключается только после импорта. OIDC overlay и тесты остаются
доступны для совместимости. Старые и новые токены не принимаются одновременно.
Откат требует согласовать изменения новых grants с прежним registry и отзывать
новые сессии; Auth revocation не отзывает токены старого IdP автоматически.

Auth добавляет сетевую зависимость для защищённых запросов: при его отказе API
возвращают отказ/503, не используют stale grants. Публичное меню и независимые
обработчики Kafka продолжают работать. Online проверка не является распределённой
транзакцией с бизнес-мутацией: уже разрешённый in-flight запрос может завершиться
во время отзыва. Длительные tracking streams ограничены сроком JWT и своими caps.

Развёртывание PWA и API на одном HTTPS origin упрощает cookies/CORS. JWT в памяти
всё ещё доступен активному XSS; BFF с серверным хранением access tokens — возможное
следующее усиление. Auth не является OAuth2/OIDC Provider и не публикует фиктивный
discovery. SMS, social login, платежи и frontend находятся вне этапа.
